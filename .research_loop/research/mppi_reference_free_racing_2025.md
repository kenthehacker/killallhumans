# Rethinking Reference Trajectories in Agile Drone Racing: A Unified Reference-Free Model-Based Controller via MPPI
- **URL**: https://arxiv.org/abs/2509.14726
- **Authors**: Fangguo Zhao, Xin Guan, Shuo Li (Zhejiang University)
- **Year**: 2025
- **Venue**: arXiv preprint

## Key Contribution

This paper proposes a **reference-free** approach to autonomous drone racing using Model Predictive Path Integral (MPPI) control. Instead of the traditional pipeline of first computing a time-optimal reference trajectory and then tracking it, the authors formulate a "gate progress" cost function that directly drives the drone toward successive gates without any precomputed trajectory. The key insight is that MPPI's sampling-based optimization can handle non-differentiable, discontinuous cost functions (like gate progress) that would be impossible with gradient-based MPC solvers. This eliminates the trajectory generation phase entirely.

The second contribution is a **unified framework** for fairly comparing three control paradigms within the same MPPI architecture: (1) trajectory tracking, (2) contouring control (MPCC-style), and (3) the proposed reference-free gate progress. By using the same dynamics model, sampling strategy, and hardware, the comparison isolates the effect of the cost function alone. The paper validates all three approaches in simulation across three tracks and in real-world flight on a 340g quadrotor running on a Jetson Orin NX.

## Technical Approach

### Quadrotor Dynamics
The state vector is 13-dimensional: position p, velocity v, quaternion q, angular velocity omega. Control inputs are rotor thrust derivatives and angular velocities, which avoids the need for a separate attitude controller. The dynamics are propagated via Euler integration at dt = 0.03s.

### MPPI Algorithm
MPPI is a sampling-based stochastic optimal control method. At each timestep:
1. M candidate control sequences are generated by adding Gaussian noise to the previous optimal sequence.
2. Each sequence is forward-simulated through the dynamics model for K steps.
3. A cost is computed for each trajectory.
4. The optimal control is a softmax-weighted average: U* = sum(w_m * U_m), where w_m = exp(-J(U_m)/lambda) / sum(exp(-J(U_i)/lambda)).

The temperature parameter lambda controls the sharpness of the weighting -- smaller lambda concentrates weight on the best trajectories.

### Gate Progress Cost (Reference-Free)
The gate progress objective is:

J_gate = sum_{k=0}^{K-1} [||p_{k+1} - p_gate||^2 - ||p_k - p_gate||^2] + Q_near * ||p_k - p_gate||^2

The first term encourages progress toward the current target gate (difference in squared distance between consecutive timesteps). The second term adds a proximity penalty near the gate to improve pass-through accuracy. A **gate switching mechanism** prevents oscillation: the gate target advances only when a geometric-temporal verification confirms the drone has crossed the gate plane consistently across control iterations.

### Trajectory Tracking Cost
Standard quadratic tracking cost:

J_track = sum_{k=0}^{K-1} [||x_k - x_{k,ref}||^2_Q + ||u_k||^2_R] + ||x_K - x_{K,ref}||^2_{Q_K}

The reference trajectory is precomputed using CPC (Complementary Progress Constraint) time-optimal planning.

### Contouring Control Cost
Decomposes position error into lag (along-path) and contouring (cross-path) components:

J_contour = sum_{k=0}^{K-1} [q_l * ||e_l||^2 + q_c * ||e_c||^2 + Q_omega * ||omega_k||^2 + r_dv * ||dv_theta||^2 + R_dT * ||dT||^2 - mu * v_theta]

The term -mu * v_theta encourages speed along the path. This is the MPCC (Model Predictive Contouring Control) formulation adapted for MPPI.

### Thrust Command Analysis
The authors show that the gate progress controller sustains maximum thrust for longer periods than tracking or contouring controllers. This aggressive behavior correlates with its ability to find more time-optimal trajectories, since it is not constrained to follow a predetermined path.

## Results

### Simulation (3 tracks: Circle, Figure-8, Split-S)

| Track | Method | Flight Time (s) | Waypoint Dist (m) | RMSE (m) |
|-------|--------|------------------|--------------------|----------|
| Circle | CPC reference | 7.29 | -- | -- |
| Circle | Tracking (Opt) | 7.65 | 0.327 | 0.25+/-0.14 |
| Circle | Tracking (MPPI) | 7.39 | 0.382 | 0.32+/-0.23 |
| Circle | Contouring (MPPI) | 7.47 | 0.484 | 0.25+/-0.13 |
| Circle | **Gate Progress** | **7.14** | 0.434 | -- |
| Fig-8 | CPC reference | 10.72 | -- | -- |
| Fig-8 | Tracking (MPPI) | 10.60 | 0.424 | 0.14+/-0.07 |
| Fig-8 | Contouring (MPPI) | 11.16 | 0.595 | 0.23+/-0.13 |
| Fig-8 | **Gate Progress** | **10.26** | 0.467 | -- |
| Split-S | CPC reference | 16.52 | -- | -- |
| Split-S | Tracking (MPPI) | 17.10 | 0.354 | 0.24+/-0.14 |
| Split-S | Contouring (MPPI) | 17.16 | 0.691 | 0.39+/-0.23 |
| Split-S | **Gate Progress** | **17.43** | 0.481 | -- |

The gate progress method achieves the **fastest flight times** on Circle and Figure-8, and is competitive on Split-S -- all without a reference trajectory. Waypoint distances are mid-range (not the tightest, but acceptable for gate passage).

### Computational Performance

| Method | Desktop RTX 3090 (ms) | Jetson Orin NX (ms) |
|--------|-----------------------|---------------------|
| Tracking (gradient-based) | 0.8 | 3.0 |
| Contouring (gradient-based) | 1.4 | 4.0 |
| MPPI (8192 samples) | 0.4 | 6.7 |

MPPI is fastest on GPU (0.4ms desktop) but slower on embedded hardware (6.7ms) due to the large sample count. Memory usage is ~500MB for MPPI.

### Real-World Results (340g quadrotor, 50Hz control)

| Method | Flight Time (s) | RMSE (m) |
|--------|-----------------|----------|
| CPC reference | 6.33 | -- |
| Contouring (gradient) | 5.84 | 0.36+/-0.14 |
| Contouring (MPPI) | 7.13 | 0.46+/-0.18 |
| **Gate Progress** | **6.56** | -- |

With reduced samples (M=2048) on embedded hardware, MPPI tracking degrades (0.46m vs 0.36m RMSE), but gate progress remains competitive at 6.56s vs the 6.33s time-optimal reference.

## Relevance to Our System

**Direct relevance is high.** Our current architecture uses precomputed min-snap trajectories followed by a PD/geometric tracker. This paper demonstrates that the trajectory generation step can be bypassed entirely with a gate progress objective inside MPPI, achieving comparable or faster race times.

**Reference-free control and trajectory non-determinism:** The gate progress approach would eliminate our trajectory optimizer entirely, removing the non-determinism introduced by trajectory re-planning. However, it introduces a different source of non-determinism: the stochastic sampling in MPPI. The paper does not report variance across runs, which is a gap.

**Computational requirements vs. our stack:** Our current PD tracker runs well above 100Hz. MPPI at 8192 samples takes 6.7ms on Jetson NX (roughly 150Hz theoretical, 50Hz in practice with overhead). Our target platform may differ, but this is a concern. The 500MB memory footprint is non-trivial. We would need GPU access on the competition platform.

**Comparison with our approach:** Our precomputed trajectory + PD tracking is simpler and more predictable. The MPPI approach is more flexible but computationally heavier. The gate progress formulation is especially interesting for scenarios where trajectory generation is unreliable or when the drone needs to recover from large deviations -- it inherently re-plans every control cycle.

**Hybrid opportunity:** We could keep our min-snap trajectory for nominal flight but use a gate-progress MPPI as a fallback controller when tracking error exceeds a threshold, or use the gate progress cost as an additional term in our existing cost function.

## Actionable Takeaways

1. **Gate progress cost function for our MPC/tracker**: Even without full MPPI, the gate progress cost J = ||p_{k+1} - p_gate||^2 - ||p_k - p_gate||^2 could be added as a feedforward term to our geometric tracker to bias it toward the next gate when off-trajectory.

2. **Gate switching logic**: The temporal-geometric gate switching mechanism (requiring consistent crossing detection across iterations) is directly applicable to improving our gate sequencer, which currently uses a simpler margin-based approach.

3. **MPPI as a replacement for min-snap + PD**: If we have GPU available on the competition platform, replacing our entire trajectory + tracking pipeline with MPPI + gate progress would simplify the architecture and potentially improve race time. The 0.4ms solve time on desktop GPU is very attractive.

4. **Contouring control as middle ground**: The MPCC-style contouring formulation within MPPI could be a stepping stone -- keep our precomputed path but use contouring control instead of pure tracking, which naturally trades tracking accuracy for speed.

5. **Aggressive thrust profiles**: The paper shows gate progress naturally finds more aggressive thrust profiles. We could analyze whether our current trajectory optimizer under-utilizes available thrust and relax our drone constraints accordingly.

6. **Reduced sample MPPI for embedded**: Even with M=2048 samples, the gate progress method works in real flight. This suggests MPPI is viable even on constrained hardware if the cost function is well-designed.

7. **Benchmark our current approach against gate progress baseline**: Implement a simple gate progress cost in our existing framework to establish whether reference-free control outperforms our current precomputed trajectory approach on our specific track configurations.

## Limitations & Caveats

- **No perception pipeline**: The paper assumes perfect state estimation and known gate positions. In our setting, we rely on EKF + PnP gate detection, so state estimation errors could amplify MPPI's stochastic behavior.

- **GPU dependency**: MPPI's parallelism requires GPU. The 6.7ms on Jetson Orin NX with only M=2048 samples shows degraded performance. Without a GPU, MPPI is impractical at competitive sample counts.

- **Memory footprint**: ~500MB for MPPI alone is significant on embedded platforms where memory is shared with perception, EKF, and other processes.

- **Variance not reported**: The paper does not discuss run-to-run variance of the stochastic MPPI controller, which is critical for competition reliability.

- **Simple tracks only**: Circle, Figure-8, and Split-S are relatively simple geometries. Performance on complex multi-gate tracks with tight sequences is unknown.

- **No obstacle avoidance**: The gate progress formulation has no notion of obstacles or forbidden regions. In competition with other drones or environmental constraints, additional cost terms would be needed.

- **50Hz control rate**: Real-world experiments run at 50Hz, which is below our 100Hz target. Whether MPPI can sustain 100Hz on competition hardware is uncertain.

- **Dynamics model fidelity**: MPPI's performance depends on the accuracy of the forward dynamics model used for rollouts. Model mismatch (aerodynamic effects, motor lag) could degrade real-world performance more than it affects a simple PD tracker.

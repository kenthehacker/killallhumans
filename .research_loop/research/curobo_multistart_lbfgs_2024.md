# cuRobo: Parallelized Collision-Free Minimum-Jerk Robot Motion Generation
**arXiv: 2310.17274**
**Authors:** Balakumar Sundaralingam et al. (NVIDIA)**
**Analyzed:** 2026-04-15

---

## 1. Key Contribution — Multi-Start L-BFGS

The central insight of cuRobo is deceptively simple: **run many independent L-BFGS optimization instances in parallel, each starting from a different seed, and return the best solution**. The authors demonstrate that this "embarrassingly parallel" strategy, combined with GPU-accelerated cost evaluation, solves difficult collision-free motion generation problems in under 50ms on average — a 60× speedup over CPU-based sequential methods.

The key claim is that prior trajectory optimization systems "fundamentally limit their ability to find better local optima by betting on a single seed." L-BFGS is a quasi-Newton local optimizer; its solution quality is entirely dependent on where it starts. For non-convex problems (collision avoidance, joint limits, kinematic constraints all introduce non-convexity), a single-start optimizer will reliably converge to a local minimum that may be far from the global optimum. cuRobo sidesteps this by running many seeds simultaneously, trading parallelism for robustness.

This approach combines three components:
1. **Particle-based initialization** — diverse seed generation via Gaussian perturbation
2. **Parallel L-BFGS with noisy line search** — GPU-batched quasi-Newton optimization
3. **Best-seed selection** — return the minimum-cost feasible solution across all seeds

## 2. Technical Approach — Parallel Multi-Start L-BFGS and the Noisy Line Search

### Standard L-BFGS Recap

L-BFGS (Limited-memory Broyden-Fletcher-Goldfarb-Shanno) approximates the inverse Hessian using a sliding window of the last `m` gradient/position pairs (history length `m`, typically 5–20). At each iteration it computes a descent direction `d = -H^{-1} * g` and then performs a line search to find a step size `α` satisfying the Wolfe conditions (sufficient decrease + curvature condition). The line search is traditionally sequential: try `α=1`, backtrack by a factor `β` until conditions are met.

### The Parallel Problem

On a GPU, sequential backtracking is a throughput killer. Each candidate step size `α` triggers a full cost + gradient evaluation across thousands of trajectory timesteps and constraint checks. Serializing these evaluations wastes the massive parallelism available.

### cuRobo's Noisy Line Search

cuRobo replaces sequential backtracking with a **parallel discrete line search**: instead of evaluating one `α` at a time, it pre-defines a fixed set of candidate step sizes and evaluates all of them simultaneously in one GPU kernel launch. The algorithm then selects the best `α` that satisfies the Armijo (sufficient decrease) condition from this batch.

The "noisy" part is the fallback: **if no candidate step size satisfies the Armijo condition**, rather than declaring line search failure and stopping, cuRobo applies a very small fixed step size (magnitude 0.01) as a "noisy perturbation." The authors justify this empirically: "the use of a noisy perturbation instead of stopping the optimization when line search fails to find a magnitude that satisfied the conditions greatly increased the convergence rate."

This is the key innovation. In standard implementations, line search failure terminates the optimizer prematurely, especially in highly constrained non-convex landscapes where the cost surface is jagged. The noisy fallback keeps all seeds alive and exploring, trading optimality guarantees for practical convergence. It is analogous to injecting gradient noise in stochastic optimization: occasional random steps escape shallow local minima.

The full per-iteration pipeline (batched over all N seeds simultaneously):
1. Compute cost and gradient for all N seeds in parallel
2. Compute L-BFGS descent direction for each seed (using per-seed history buffers)
3. Evaluate M discrete step sizes for each seed in parallel (N × M evaluations)
4. Select best valid step; fall back to noisy step (α=0.01) if none satisfy Armijo
5. Update all N seeds in parallel

### Seed Initialization via Particle Sampling

Seeds are initialized using a particle-based approach. A mean trajectory `Θ_μ` and covariance `Θ_σ` are defined, then `n` particles are sampled as:

```
θ_{n,[1,T]} = Θ_μ + Θ_σ * θ_s
```

where `θ_s` is drawn from a zero-mean Gaussian. This creates diverse but geometrically coherent starting points, each representing a plausible trajectory that the L-BFGS optimizer can refine. Additional seeds are generated by:
- Linear interpolation between start configuration and IK-solved goal configurations
- Interpolation through a predefined "retract" (home) configuration
- Output of a parallel geometric planner (RRT-style, 101× faster than RRTConnect)

## 3. Number of Parallel Seeds and Selection Criteria

### Seed Counts

cuRobo uses **different seed counts for different tasks**:

- **Trajectory optimization:** 12 seeds (from Table 3: "Time taken by kernels in 1 iteration of Trajectory Optimization (12 seeds, 32 timesteps)")
- **Inverse kinematics (IK):** 30 seeds ("For all cuRobo IK queries, we run 30 seeds in parallel and return the best solution from these seeds")

The trajectory optimization uses 32 timesteps per seed. The IK solver uses 30 seeds because the IK problem is lower-dimensional (joint space only) and the solution space has more local minima from redundancy.

Section 7.2 of the paper specifically analyzes the "Effect of Parallel Seeds" as an ablation, confirming that seed count is a critical hyperparameter. The overall benchmark uses 2,600 motion planning problems to establish statistical significance.

### Selection Criteria

The selection criterion is straightforward **minimum cost among all seeds that achieve feasibility**. A solution is considered successful if it is:
- Collision-free (zero penetration with obstacles)
- Within joint limits
- Within 5mm of target position
- Within 5° of target orientation

Among seeds satisfying these constraints, the one with minimum total cost (weighted sum of trajectory time + constraint violations) is returned. If no seed is fully feasible, the least-infeasible seed is returned (graceful degradation).

## 4. Results — Single-Start vs. Multi-Start Success Rate

cuRobo achieves a **99.8% success rate** across 2,600 motion planning problems, compared to 98.53% for Tesseract (a leading CPU-based trajectory optimizer). Failures: cuRobo failed on 5 problems; Tesseract failed on 38 problems.

The speedup is 60× on average over CPU-based methods (50ms vs ~3 seconds), while simultaneously improving quality: generated trajectories have 1.23× lower time and 4× lower maximum jerk than the baseline.

While the paper does not provide a direct A/B table of "single-start L-BFGS vs. multi-start L-BFGS success rate" with exactly the same hardware, the theoretical argument and the Section 7.2 ablation both point to multi-start as the dominant factor in the success rate improvement. A single-start L-BFGS is at the mercy of its initialization; with 12–30 seeds, the probability that at least one seed lands in a basin of attraction near a good local minimum is dramatically higher.

The other major result: the **parallel geometric planner** (used to seed trajectory optimization) achieves 101× speedup over RRTConnect, meaning high-quality initializations are essentially free.

## 5. Relevance to Our Drone Racing Trajectory Optimizer

Our current optimizer in `/planning/trajectory_optimizer.py` uses a single call to `scipy.optimize.minimize` with `method="L-BFGS-B"`:

```python
result = minimize(
    objective,
    log_times,          # single initial guess: log of distance-based time estimates
    method="L-BFGS-B",
    options={"maxiter": 200, "ftol": 1e-6},
)
```

The initial guess `log_times` comes from a single distance-based heuristic (`_initial_time_allocation`). If this heuristic lands in a poor basin — e.g., a local minimum where one segment is over-allocated and another is starved — the optimizer may converge to a suboptimal solution with no way to escape.

Our objective function is non-convex because:
- The velocity constraint penalty `(avg_v - max_v)^2` activates discontinuously
- The acceleration penalty couples adjacent segment pairs nonlinearly
- The FOV tilt penalty `(tilt - half_fov)^2` is highly nonlinear in segment times
- The `log_times` reparametrization helps positivity but does not convexify the landscape

The cuRobo insight directly applies: **running multiple L-BFGS-B calls from perturbed initial conditions, then selecting the best result, will improve both the optimality of the final trajectory and robustness against bad initializations.** We already see evidence of sensitivity to initialization in the per-gate error variance (e.g., gate-4 error fluctuating ±5% across iterations while other gates are stable).

## 6. Actionable Takeaways — Sequential Multi-Start L-BFGS (No GPU)

Without a GPU, we cannot parallelize the seed evaluations. However, sequential multi-start is straightforward and well-understood. The gains come from exploring multiple basins, not from wall-clock parallelism.

**Algorithm (drop-in replacement for `_optimize_time_allocation`):**

```python
def _optimize_time_allocation_multistart(
    self,
    waypoints: List[np.ndarray],
    initial_times: List[float],
    start_velocity: Tuple[float, float, float],
    n_seeds: int = 8,
    perturbation_scale: float = 0.3,
) -> List[float]:
    """Multi-start L-BFGS-B for time allocation optimization."""
    rng = np.random.default_rng(seed=42)
    log_times_base = np.log(np.array(initial_times))

    best_result = None
    best_cost = float("inf")

    # Seed 0: original heuristic (no perturbation)
    seeds = [log_times_base.copy()]

    # Seeds 1..n_seeds-1: Gaussian perturbations
    for _ in range(n_seeds - 1):
        noise = rng.normal(0, perturbation_scale, size=len(log_times_base))
        seeds.append(log_times_base + noise)

    for seed in seeds:
        result = minimize(
            objective,
            seed,
            method="L-BFGS-B",
            options={"maxiter": 200, "ftol": 1e-6},
        )
        if result.fun < best_cost:
            best_cost = result.fun
            best_result = result

    optimized_times = np.exp(best_result.x)
    optimized_times = np.maximum(optimized_times, 0.1)
    return optimized_times.tolist()
```

**The "noisy line search" idea for CPU:** scipy's L-BFGS-B uses its own line search internally which we cannot easily replace. However, the spirit of the noisy fallback is already captured by running multiple seeds — if one seed gets stuck in a bad basin (line search stalls), other seeds started from different points will not share that failure mode.

**Warm-starting between race laps:** cuRobo seeds from previous solutions in online settings. We can similarly cache the best `log_times` result and use it as an additional seed in subsequent planning calls, giving us "warm-start + multi-start" — the warm start exploits track continuity while fresh perturbations still explore.

**Cost landscape smoothing:** The noisy line search in cuRobo works partly because the small noisy steps smooth out numerical discontinuities in the cost. We can approximate this by softening our penalty functions — replacing hard quadratic activation with smooth exponential penalties that have gradients everywhere. This improves L-BFGS convergence for any starting point.

## 7. Key Parameters

### Number of Seeds

| Setting | cuRobo value | Recommended for us |
|---------|-------------|-------------------|
| Trajectory optimization seeds | 12 | 6–10 (sequential, so budget matters) |
| IK seeds | 30 | N/A (we don't solve IK) |
| Timesteps per seed | 32 | Our segments: 8–12 |

For sequential execution, **8 seeds** balances exploration vs. latency. Our trajectory optimizer runs once at startup (not in the control loop), so even 16 seeds adds only ~2× planning time — acceptable.

### Perturbation Magnitude

cuRobo uses Gaussian sampling in trajectory space. In our log-time space, a standard deviation of `σ = 0.3` corresponds to multiplicative factors of `exp(±0.3) ≈ ×1.35` on each segment time — large enough to escape local minima but not so large that seeds are completely infeasible.

Recommended schedule:
- Seed 0: σ = 0 (original heuristic)
- Seeds 1–3: σ = 0.2 (small perturbation, exploits nearby basins)
- Seeds 4–6: σ = 0.4 (medium perturbation, wider exploration)
- Seed 7: σ = 0.8 (large perturbation, escape far-away optima)

This mixed-scale strategy is similar to population-based methods and ensures coverage at multiple resolution scales.

### Selection Criteria

cuRobo selects minimum-cost feasible solution. For us:
1. **Primary filter:** reject any solution where `max(optimized_times) < 0.1` or any constraint violation exceeds threshold
2. **Selection:** among feasible solutions, pick `argmin(objective_value)` — the same objective used during optimization, so no separate evaluation needed
3. **Tie-breaking:** prefer solutions with lower total time (already captured in objective with `time_weight=2.3`)

### L-BFGS-B History Length

cuRobo's Section 7.4 analyzes L-BFGS history length (parameter `m`). The default in scipy's L-BFGS-B is `m=10`. For our 8–12 dimensional problem (one log-time per segment), history length 5–10 is sufficient — increasing beyond 10 adds computational cost with diminishing returns.

### Convergence Tolerance

Our current `ftol=1e-6` is aggressive. For multi-start, we could loosen to `ftol=1e-5` per seed (faster per-seed convergence) and rely on the best-of-N selection to compensate for slightly premature termination of individual seeds. This allows more seeds within the same time budget.

## Summary and Priority

The cuRobo multi-start L-BFGS paper provides strong empirical and theoretical justification for replacing our single-start optimizer with a multi-start version. The change is minimal (wrap `minimize` in a loop, add Gaussian perturbation), requires no new dependencies, and directly addresses the observed sensitivity to initialization in our per-gate error profiles.

**Recommended implementation order:**
1. Implement 8-seed sequential multi-start in `_optimize_time_allocation` (30 min, high confidence)
2. Add mixed-scale perturbation (σ = 0.2, 0.4, 0.8) rather than fixed σ
3. Cache best result for warm-starting across re-plan calls
4. Optionally soften penalty functions for smoother L-BFGS convergence

Expected gain: more consistent per-gate times, reduced variance in tracking error, potential 5–15% improvement in worst-case gate errors (gates 4, 7 which show high variance).

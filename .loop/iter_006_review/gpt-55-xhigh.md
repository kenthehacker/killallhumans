# Iter 006 Adversarial Review — GPT-5.5 Extra High

## Summary
Iter-006 improves the synthetic matrix, but the speed fix is still not a single competition-wide behavior: synthetic derives velocity from gate geometry while PyBullet, visual demo, and the competition-facing pipeline still use separate fixed/config defaults. I also found that the new airspace and matrix-strict checks are narrower than advertised: bounds are hard-coded to bench z-up semantics, placeholder tracks skip the plan-validation strictness, and missing plan-validation data is treated as acceptable.

## Findings (ordered by severity)

### F1. Auto-derived velocity only reaches the synthetic benchmark; PyBullet and RacePipeline still use independent speed sources — [BLOCKER]
- **File(s)**: `scripts/benchmark.py:337`, `scripts/benchmark.py:806`, `sim_pybullet/env.py:19`, `race_pipeline.py:89`, `race_pipeline.py:245`, `scripts/visual_demo.py:385`
- **Issue**: The core iter-006 claim is that `derive_safe_max_velocity()` replaced the old fixed/per-track velocity magic numbers, but that is only true for `run_synthetic_benchmark()`. The synthetic path reads a top-level `max_velocity_mps` override or derives from gate geometry (`scripts/benchmark.py:337-347`). The PyBullet path still chooses `getattr(race_config, "max_velocity_mps", None) or planner_cfg.plan_max_speed_mps` (`scripts/benchmark.py:806-809`), but `RaceConfig` has no `max_velocity_mps` field (`sim_pybullet/env.py:19-38`) and `load_config()` never carries that top-level key (`sim_pybullet/env.py:217-228`). The competition-facing `RacePipeline` still defaults to `PipelineConfig.max_speed = 8.0` (`race_pipeline.py:89-96`) and feeds that directly into `SpeedProfiler` / `DroneConstraints` (`race_pipeline.py:245-257`). The visual demo remains on `planner_cfg.plan_max_speed_mps` (`scripts/visual_demo.py:385-395`). That means the matrix can pass at a geometry-derived speed while the actual sim/competition path flies a different trajectory.
- **Repro**: Use any config without a top-level `max_velocity_mps` such as `slalom.json`, whose note says iter-006 removed the explicit override (`sim_pybullet/configs/slalom.json:1-2`). Synthetic derives from the gate triplets; PyBullet falls through to `PlannerConfig.plan_max_speed_mps` default 4.0 (`planning/trajectory_optimizer.py:597-604`); `RacePipeline` flies at 8.0 unless a caller manually overrides. For `race_01`, the mismatch is also visible: synthetic ignores `planner.plan_max_speed_mps: 4.0` and derives/uses geometry, while PyBullet uses the planner value from `race_01.json:48-57`.
- **Fix sketch**: Introduce one canonical speed-selection helper, e.g. `select_plan_max_velocity(gates, config, explicit_override=None)`, and call it from synthetic, PyBullet, visual demo, and `RacePipeline.configure()`. Make `max_velocity_mps` (or a better-named planner field) first-class in `RaceConfig`, or delete the top-level convention and put the derived value into `PlannerConfig` before all planners are constructed. Add a fast plumbing test that loads `slalom.json` and `race_01.json` through synthetic/PyBullet/RacePipeline setup and asserts the chosen max velocity is identical.
- **Confidence**: high — the relevant call sites are static and disagree on which field/default feeds `DroneConstraints.max_velocity`.

### F2. Airspace validation ignores per-track field bounds and bakes z-up semantics into a reusable validator — [MAJOR]
- **File(s)**: `planning/plan_validator.py:53`, `planning/plan_validator.py:88`, `planning/plan_validator.py:132`, `scripts/benchmark.py:359`, `scripts/benchmark.py:509`, `sim_pybullet/configs/slalom.json:3`, `sim_pybullet/configs/figure8.json:2`
- **Issue**: `validate_trajectory()` defaults to `ground_z_threshold=0.05` and `ceiling_z_threshold=20.0` (`planning/plan_validator.py:53-61`) and fails on `pos[2] < ground` / `pos[2] > ceiling` (`planning/plan_validator.py:132-138`). The synthetic bench calls it without passing bounds (`scripts/benchmark.py:358-359`), so every track gets the same [0.05, 20.0] z envelope. That matches the bench's hard-coded crash checks (`scripts/benchmark.py:507-515`), but it ignores each config's actual `field.bounds_max.z`: `slalom` and `figure8` both cap z at 5.0 (`sim_pybullet/configs/slalom.json:3-6`, `sim_pybullet/configs/figure8.json:2-5`). A trajectory at z=10 on slalom is outside the course but will not be flagged by plan validation or the synthetic crash check.
- **Repro**: Build a stub trajectory for `slalom` that passes all gates geometrically but cruises at z=10.0. With the current `validate_trajectory(traj, gates, dt=...)` call, the airspace check does not fire because 10.0 is below the global 20.0 ceiling, even though the track config says the field max z is 5.0. Conversely, if this validator is reused against NED-style pipeline inputs (the codebase still has sequencer tests at z=-2.0 in `gate_sequencing/tests/test_sequencer_adversarial.py:35-44`), the default ground check would immediately report `crash_ground`.
- **Fix sketch**: Thread `field.bounds_min[2]` / `field.bounds_max[2]` from the track config into both the validator and the synthetic crash check. Make the coordinate convention explicit in the API name or config adapter: either `validate_trajectory_z_up(...)` for bench-only use, or normalize all inputs to the validator's frame before checking. Add tests for a track with `bounds_max.z=5.0` and for rejecting accidental NED input with a clearer diagnostic.
- **Confidence**: high for the missed per-track bounds; medium for the NED reuse risk because the current validator call site is synthetic/z-up only, but the function is intentionally generic and likely to be reused.

### F3. `benchmark_matrix` still lets illegal or missing plan validation pass for important cases — [MAJOR]
- **File(s)**: `scripts/benchmark_matrix.py:87`, `scripts/benchmark_matrix.py:104`, `scripts/benchmark_matrix.py:134`, `sim_pybullet/configs/aigp_default.json:1`
- **Issue**: The iter-006 brief says the matrix now marks a track regressed when `sim_passed=True` but `plan_validation.ok=False`, but that only applies in the non-placeholder branch. Placeholder tracks branch at `is_placeholder` and only check `gate_pass_rate < 50%` (`scripts/benchmark_matrix.py:104-112`); the `plan_validation.ok` check lives exclusively in the production-track branch (`scripts/benchmark_matrix.py:129-139`). The AIGP placeholder is exactly the stand-in for future competition geometry (`sim_pybullet/configs/aigp_default.json:1-5`), so allowing it to report PASS with an illegal plan weakens the one track meant to smoke-test AIGP defaults. The same code also treats missing plan-validation data as OK: `pv = track_summary.get("plan_validation") or {}` followed by `pv.get("ok") is False` (`scripts/benchmark_matrix.py:134-135`) means `None`, `{}`, or absent `"ok"` do not fail.
- **Repro**: Force `run_synthetic_benchmark()` to return `{"sim_passed": True, "gate_pass_rate": 1.0, "plan_validation": {"ok": False, "reason": "DQ"}}` for `aigp_default`. Because it is marked `placeholder: true`, `run_matrix()` will not append a regression. Similarly, if a future benchmark error drops the `plan_validation` field entirely, production tracks fall through because `pv.get("ok")` is `None`, not `False`.
- **Fix sketch**: Make plan validation a separate acceptance gate applied to every track summary, before placeholder relaxation. If placeholders need looser gate-rate thresholds, keep only that relaxation; do not waive illegal plans. Treat missing `plan_validation` or missing `"ok"` as a regression (`missing plan_validation`) so schema drift cannot silently pass.
- **Confidence**: high — this is directly visible in the matrix control flow.

### F4. Small but real bends below 5 degrees are ignored, which can over-speed close-gate courses — [MAJOR]
- **File(s)**: `planning/auto_velocity.py:46`, `planning/auto_velocity.py:111`, `planning/auto_velocity.py:118`, `tests/test_auto_velocity.py:60`
- **Issue**: `_MIN_BEND_RAD = 5°` causes every triplet below that bend to be skipped (`planning/auto_velocity.py:46-49`, `planning/auto_velocity.py:111-112`). If all triplets are below 5°, the function returns the absolute cap (`planning/auto_velocity.py:118-123`). That is fine for race_01-scale 10m spacing, but it is not generally safe: close gates with a 4.9° bend can still impose a meaningful centripetal limit. For example, at 0.5m spacing and 4.9°, the current formula gives `r ≈ 0.5 / (2*sin(2.45°)) ≈ 5.85m`, so `sqrt(15*5.85)*0.8 ≈ 7.5m/s`, not 15m/s. The current tests cover a 15° gentle bend at 10m spacing (`tests/test_auto_velocity.py:60-71`) but not the close-gate shallow-bend case.
- **Repro**: Three gates at `(0,0,2)`, `(0.5,0,2)`, and `(0.5 + 0.5*cos(4.9°), 0.5*sin(4.9°), 2)` return `DEFAULT_ABSOLUTE_CAP_MPS` today because the only measurable bend is skipped. The physics formula itself would produce a binding speed below the cap.
- **Fix sketch**: Do not skip a bend merely because it is below 5°. Instead compute the radius for every non-degenerate triplet and only ignore it if the resulting `v_safe >= absolute_cap_mps` (i.e. it truly cannot bind). Keep a tiny epsilon around `sin(bend/2)` only to avoid numeric explosion for exactly straight lines. Add unit tests for close shallow bends, exactly straight lines, and the known 90°/1m case (`r = 1/sqrt(2) ≈ 0.707m` under the current inscribed-arc approximation).
- **Confidence**: medium-high — the exact track geometry may not include 0.5m spacing, but the code is supposed to generalize to unknown courses and the current threshold is a hidden geometry assumption.

### F5. The absolute cap and safety factor are parameterized, but still not validated against the drone model or matrix targets — [MINOR]
- **File(s)**: `planning/auto_velocity.py:29`, `planning/auto_velocity.py:35`, `planning/auto_velocity.py:41`, `tests/test_auto_velocity.py:101`
- **Issue**: `DEFAULT_DRONE_MAX_ACCEL=15.0`, `DEFAULT_SAFETY_FACTOR=0.8`, and `DEFAULT_ABSOLUTE_CAP_MPS=15.0` are now named constants and function parameters, which is better than the removed per-track literals. But the justifications are still bench/legacy based (`planning/auto_velocity.py:29-44`), not derived from the current vehicle or track config. The tests assert scaling when callers pass a different safety factor or acceleration (`tests/test_auto_velocity.py:101-117`), but no test or benchmark guard proves the defaults are correct for the PyBullet Crazyflie model, the DCL competition drone, or the `<14s` aspirational race-time target. This is probably acceptable as a first replacement for 8/6, but it should not be treated as fully satisfying the charter's "no magic numbers" rule.
- **Repro**: `race_01` is now reported at ~18.1s in the brief, slower than the 13.7s v=15 baseline and above the CLAUDE.md aspirational target. The code comments say the cap is "aligned with the legacy default" (`planning/auto_velocity.py:41-44`) and the safety factor leaves "20-30%" margin (`planning/auto_velocity.py:35-39`), but neither value is tied to a measured acceleration envelope or a per-track validation result.
- **Fix sketch**: Keep these as defaults but surface them through a calibrated vehicle profile (`DroneConstraints.max_acceleration`, measured thrust/tilt limits, or config). Add a matrix report column for chosen `max_velocity` and a regression gate on race time so a safer-but-too-slow default is an explicit tradeoff, not accidental drift.
- **Confidence**: medium — these are better than the removed literals, but the remaining empirical constants still need calibration and visibility.

## Things iter-006 got right

- Degenerate zero-length adjacent segments are skipped safely, avoiding a division-by-zero path (`planning/auto_velocity.py:101-104`, `tests/test_auto_velocity.py:88-98`).
- The validator now catches the bench's ground and ceiling crashes for the synthetic z-up convention (`planning/plan_validator.py:129-138`, `tests/test_plan_validator.py:200-239`).
- Non-placeholder production tracks now fail the matrix when `plan_validation.ok` is explicitly false (`scripts/benchmark_matrix.py:129-139`), closing the core iter-005 matrix-strict gap for those tracks.
